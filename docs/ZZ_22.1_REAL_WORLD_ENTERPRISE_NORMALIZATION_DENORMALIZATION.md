## 🎯 Nguyên Tắc Xương Sống

Production guide 2026 của JusDB tóm tắt rất gọn, trùng khớp với phần "Hybrid Approach" trong file ZZ_22:

> **"Start with 3NF for every new OLTP schema. Denormalize only when you have concrete evidence that JOIN cost exceeds the cost of maintaining the denormalized copy."**

Quy trình chuẩn của enterprise:

1. **Mặc định normalize (3NF)** cho core transactional data — đảm bảo integrity, write đơn giản.
2. **Chỉ denormalize khi có bằng chứng đo được**, ví dụ:
   - Một JOIN-heavy query trên bảng vài tỷ rows chạy > 5 giây và nằm trên **hot path**.
   - Bạn đang phải trả tiền cho read replica chỉ để gánh tải JOIN.
3. **Tuyệt đối không dựa vào application code** để giữ consistency cho dữ liệu denormalized → đây chính là điểm file ZZ_22 cảnh báo ở mục "Data Synchronization Race Conditions".

> 💡 Câu nói kinh điển: **"Normalize until it hurts, denormalize until it works."**

## 🧭 CAP & PACELC — Nền Tảng Lý Thuyết Của Mọi Trade-off

Trước khi đọc các case study, cần nắm 2 định lý làm "kim chỉ nam" cho mọi quyết định denormalize ở scale phân tán. Đây chính là lý do **Discord chọn AP** còn **Uber chọn CP**.

### CAP Theorem (Eric Brewer, 2000)

Một hệ phân tán **chỉ chọn được 2 trong 3** khi xảy ra network partition:

```text
        Consistency (C)
       /              \
      /                \
Availability (A) ──── Partition tolerance (P)

Mạng phân tán LUÔN có thể bị partition (P là bắt buộc).
=> Thực tế chỉ còn chọn giữa C và A khi partition xảy ra.
```

| Lựa chọn                      | Ý nghĩa                                                    | Hệ tiêu biểu                                           |
| ----------------------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| **CP** (hy sinh Availability) | Khi partition → từ chối phục vụ để không trả dữ liệu sai   | PostgreSQL (single-primary), MongoDB (majority), HBase |
| **AP** (hy sinh Consistency)  | Khi partition → vẫn phục vụ, chấp nhận dữ liệu cũ tạm thời | Cassandra, DynamoDB, Riak                              |

### PACELC — Phần CAP Bỏ Quên (Daniel Abadi, 2012)

CAP chỉ nói về lúc **có partition**. PACELC bổ sung phần **bình thường (Else)**:

```text
IF Partition (P):  trade-off giữa  Availability (A) ↔ Consistency (C)
ELSE (E):          trade-off giữa  Latency      (L) ↔ Consistency (C)
```

> **Insight cốt lõi:** Ngay cả khi mạng khỏe mạnh, bạn vẫn phải đánh đổi **độ trễ** lấy **độ nhất quán**. Muốn đọc nhanh (low latency) → thường phải chấp nhận đọc bản denormalized hơi cũ. Đây chính là bản chất của việc denormalize.

| Hệ                       | Phân loại PACELC       | Diễn giải                                                         |
| ------------------------ | ---------------------- | ----------------------------------------------------------------- |
| **Cassandra / DynamoDB** | **PA/EL**              | Partition → ưu tiên Available; Bình thường → ưu tiên Latency thấp |
| **PostgreSQL / MySQL**   | **PC/EC**              | Luôn ưu tiên Consistency, kể cả khi phải chậm hơn                 |
| **MongoDB**              | **PA/EC** (tùy config) | Linh hoạt theo read/write concern                                 |

### 🎯 Liên hệ với denormalization

- **Denormalize = chủ động dịch sang phía EL/AP** cho một phần dữ liệu (read model) để đổi lấy latency thấp.
- **Write model giữ EC/CP** (PostgreSQL trong dự án này) để bảo toàn invariant.
- Mỗi case study dưới đây thực chất là một điểm khác nhau trên trục **PACELC**.

## 🔧 4 Kỹ Thuật Giữ Consistency Cho Dữ Liệu Denormalized

| Kỹ thuật                 | Bản chất                                               | Khi nào dùng                                     | Map với ZZ_22                              |
| ------------------------ | ------------------------------------------------------ | ------------------------------------------------ | ------------------------------------------ |
| **Materialized Views**   | DB tự tính sẵn, refresh theo lịch                      | Reporting, listing                               | Mục "Materialized Views"                   |
| **DB Triggers**          | Tự cập nhật cột denormalized khi INSERT/UPDATE         | Counter cache (reviewCount, averageRating)       | Mục "Counter Caching Implementation"       |
| **CDC / Debezium**       | Stream thay đổi từ OLTP → OLAP (ClickHouse, StarRocks) | Tách hẳn write/read system                       | Mục "CQRS"                                 |
| **Transactional Outbox** | Ghi event vào cùng transaction với data, relay sau     | Khi cần phát event/sync mà KHÔNG mất consistency | Mục "Data Synchronization Race Conditions" |

> JusDB nhấn mạnh: _"Materialized views are the modern way to denormalize for read performance — no application-side sync code, no integrity bugs."_
>
> Cảnh báo quan trọng: _"Never rely on application-code consistency for denormalization."_

> ⚠️ **Vì sao thêm Transactional Outbox?** 3 kỹ thuật đầu phù hợp khi nguồn và đích **cùng một database**. Khi bạn phải cập nhật **2 hệ thống tách rời** (DB + message broker, DB + search index, DB + cache), bạn rơi vào **dual-write problem** — xem mục kế tiếp.

## 📨 Dual-Write Problem & Transactional Outbox Pattern

> Đây là **lỗ hổng phổ biến nhất** khi denormalize qua nhiều hệ thống — và liên quan trực tiếp tới `DomainEvent` (fire-and-forget) đang dùng trong dự án này.

### Dual-Write Problem là gì?

Khi một thao tác cần ghi vào **2 nơi không cùng transaction** (ví dụ: PostgreSQL + RabbitMQ/Redis), không có cách nào đảm bảo cả hai cùng thành công:

```text
async createOrder() {
  await prisma.order.create(...)        // ① DB commit OK
  await eventBus.publish(OrderCreated)  // ② broker DOWN → MẤT EVENT
}
// Hậu quả: Order tồn tại trong DB nhưng read-model / email / inventory
//          KHÔNG bao giờ được cập nhật → inconsistency vĩnh viễn.
```

Đảo thứ tự cũng không cứu được:

```text
  await eventBus.publish(OrderCreated)  // ① publish OK
  await prisma.order.create(...)        // ② DB FAIL → event "ma", order không tồn tại
```

> ⚠️ Đây chính xác là rủi ro của comment trong `src/events/domain-event.base.ts`:
> _"Events are fire-and-forget for post-transaction side effects."_
> Fire-and-forget = nếu handler chạy sau khi commit mà process crash, **event biến mất**.

### Giải pháp: Transactional Outbox

Ghi event vào một **bảng `outbox` trong CÙNG transaction** với business data. Một tiến trình riêng (relay/poller) đọc bảng đó rồi publish ra broker. Vì cùng transaction → **atomic**: hoặc cả order + event cùng tồn tại, hoặc cả hai cùng rollback.

```text
┌──────────── ONE DB TRANSACTION ────────────┐
│  INSERT INTO "Order"   (...)                │
│  INSERT INTO "Outbox"  (eventType, payload) │  ← atomic, cùng commit
└─────────────────────────────────────────────┘
                  │
                  ▼  (tách biệt, async)
   ┌─────────────────────────────┐
   │ Outbox Relay / Poller        │
   │  - đọc rows chưa publish     │
   │  - publish ra broker         │
   │  - đánh dấu processedAt      │
   └─────────────────────────────┘
                  │
                  ▼
            Message Broker → handlers (email, read-model, inventory)
```

### Schema gợi ý (Prisma)

```prisma
model Outbox {
  id          Int       @id @default(autoincrement())
  aggregateId String                              // vd: orderId
  eventType   String    @db.VarChar(200)          // vd: "order.created"
  payload     Json                                // toàn bộ event data
  occurredAt  DateTime  @default(now())
  processedAt DateTime?                            // null = chưa relay
  attempts    Int       @default(0)
  @@index([processedAt, occurredAt])              // poll rows chưa xử lý
}
```

### Delivery semantics: At-least-once + Idempotency

Outbox đảm bảo **at-least-once delivery** (event có thể được publish > 1 lần nếu relay crash giữa publish và đánh dấu `processedAt`). Vì vậy **handler phải idempotent**:

```text
- Dùng eventId (đã có sẵn randomUUID trong DomainEvent) làm dedup key.
- Handler kiểm tra "đã xử lý eventId này chưa?" trước khi side-effect.
- Hoặc dùng upsert thay vì insert để thao tác lặp lại vô hại.
```

### So sánh nhanh

| Cách tiếp cận                 | Atomic? | Mất event?         | Độ phức tạp                     |
| ----------------------------- | ------- | ------------------ | ------------------------------- |
| Fire-and-forget (hiện tại)    | ❌      | Có thể (nếu crash) | Thấp                            |
| 2PC / Distributed TX          | ✅      | Không              | Rất cao, chậm, khó scale        |
| **Transactional Outbox**      | ✅      | Không              | Vừa phải — **được khuyến nghị** |
| CDC trên chính bảng nghiệp vụ | ✅      | Không              | Cần Debezium + Kafka            |

> 🎓 **Bài học:** Khi denormalize/sync ra ngoài database (read model, search, cache, email), đừng tin vào fire-and-forget. Outbox là cách rẻ nhất để biến "best-effort" thành "guaranteed eventual consistency".

## Case Study 1: Discord — Denormalization + Bucketing trên Cassandra

> **Case study kinh điển nhất** về cân bằng performance vs consistency ở scale hàng tỷ message.

### Bối cảnh

- Read/write ratio ~ **50/50** và read **cực kỳ random**.
- Server voice-chat-heavy gửi rất ít message; server text-heavy gửi hàng nghìn message/giây.

### Denormalize có chủ đích

- Dùng Cassandra **KKV store** (key-key-value).
- Primary key **tiến hóa** theo thời gian để giải bài toán partition size:

```text
(channel_id, message_id)              ❌ partition vượt 100MB → GC pressure
        ↓
((channel_id, bucket), message_id)    ✅ bucket theo cửa sổ ~10 ngày
```

- **Bucketing** giữ mỗi partition < 100MB nhưng vẫn query được.

### Đánh đổi consistency (AP thay vì CP)

- Chọn **Availability + Partition tolerance** thay vì strong consistency.
- Kết quả: **write sub-millisecond**, **read < 5ms**, API response < 80ms.

### Cách giữ nhất quán mà KHÔNG read-before-write

- Mọi write là **upsert** → "xóa column" và "ghi null" đều tạo **tombstone**.
- Tối ưu: chỉ ghi giá trị **non-null** → giảm tombstone từ ~12 xuống ~0 mỗi message.
- **Anti-entropy repair chạy hàng đêm** + phát hiện row hỏng (thiếu field bắt buộc) rồi xóa.
- Hạ **tombstone lifespan** từ 10 ngày → 2 ngày; query code track các bucket rỗng để né.

### 🎓 Bài học

Chấp nhận **eventual consistency tạm thời** để đổi lấy độ trễ thấp ổn định ở scale khổng lồ. Đây đúng là _"art of balance"_ mà file ZZ_22 kết luận.

## Case Study 2: Instagram — Fan-out-on-write

> Pattern denormalize **read model** điển hình cho hệ thống read-heavy.

### Bối cảnh

- Feed **read-heavy cực mạnh**: user scroll nhiều hơn post rất nhiều.
- Mỗi feed item chứa nhiều media (ảnh, video, caption, comment, like).

### Giải pháp: Fan-out-on-write

```text
❌ Fan-out-on-read:  JOIN nhiều bảng MỖI LẦN đọc feed → chậm
✅ Fan-out-on-write: precompute + ghi sẵn feed item vào nhiều đích
                     NGAY LÚC tác giả post
```

- Dữ liệu được **precompute và ghi sẵn** lúc write, đọc feed chỉ việc lấy ra.
- Đây chính là **CQRS Read Model** trong ZZ_22: write model normalized, read model denormalized để query siêu nhanh.

### 🎓 Bài học

Khi read >> write, hãy **dời chi phí JOIN từ read-time sang write-time**. Đổi lại phải chấp nhận thêm storage và logic fan-out.

## Case Study 3: Twitter — Hybrid Fan-out & Bài Toán Celebrity

> Phần **tiến hóa** của Instagram fan-out: khi pure fan-out-on-write gặp giới hạn.

### Vì sao fan-out-on-write thuần túy "vỡ trận"

Instagram fan-out-on-write rất ngon cho user thường. Nhưng với **celebrity** (Taylor Swift, Ronaldo) có hàng chục triệu follower:

```text
1 tweet của celebrity 100M follower
   = 100 TRIỆU lần ghi vào 100 TRIỆU feed
   → "fan-out storm": write amplification khổng lồ, feed của fan trễ hàng phút
```

### Giải pháp Hybrid (kết hợp 2 chiến lược)

```text
┌─────────────────────────────────────────────────────────────┐
│ User THƯỜNG  →  Fan-out-on-WRITE                              │
│   push tweet vào feed của follower ngay lúc post (đọc nhanh)  │
├─────────────────────────────────────────────────────────────┤
│ CELEBRITY    →  Fan-out-on-READ                               │
│   KHÔNG push; tweet để nguyên, MERGE vào feed lúc fan mở app  │
└─────────────────────────────────────────────────────────────┘
        ↓
Feed cuối = (precomputed feed) MERGE (tweet mới của các celebrity đang follow)
```

- Tránh được fan-out storm: tweet celebrity không nhân bản hàng triệu lần.
- Fan thường vẫn đọc cực nhanh nhờ phần precomputed.

### 🎓 Bài học

**Không có chiến lược denormalize nào đúng cho 100% dữ liệu.** Phải **phân loại theo đặc tính phân phối** (skew/hot key) và áp dụng chiến lược lai. Đây là bản nâng cấp của bài học Instagram: read-heavy → denormalize, nhưng phải xử lý riêng **hot key**.

## Case Study 4: Uber — High-throughput Payment với Strict Consistency

> Phía **ngược lại** của Discord: domain tài chính KHÔNG hy sinh consistency.

### Bối cảnh

- Xử lý **> 30 update/giây mỗi user account**.
- Tiền bạc → **strict consistency** là bắt buộc, sai một xu cũng không được.

### Giải pháp

- **Batch processing** + **concurrency control** thay vì denormalize bừa bãi.
- Giữ chặt invariants thay vì chạy theo tốc độ read.

### 🎓 Bài học

**Domain quyết định trade-off:**

| Domain                    | Lựa chọn                | Ví dụ                       |
| ------------------------- | ----------------------- | --------------------------- |
| Chat / Feed / Analytics   | Eventual consistency OK | Discord, Instagram, Twitter |
| Payment / Order / Invoice | Strict consistency      | Uber, `ProductSKUSnapshot`  |

Giống mục **ProductSKUSnapshot** trong ZZ_22: hóa đơn phải chính xác tuyệt đối tại thời điểm mua vì **legal compliance**.

## Case Study 5: Amazon DynamoDB — Single-Table Design

> Cực điểm của denormalize: gộp **nhiều entity vào MỘT bảng** để đạt single-digit millisecond ở mọi scale.

### Bối cảnh

- DynamoDB là NoSQL key-value/document, **không hỗ trợ JOIN**.
- Triết lý của AWS (Rick Houlihan): _"In NoSQL you model for your access patterns, not your entities."_

### Single-Table Design

Thay vì mỗi entity một bảng (như RDBMS), nhồi **User, Order, OrderItem...** vào **một bảng duy nhất**, phân biệt bằng partition key (PK) + sort key (SK) được "overload":

```text
PK              SK                  Attributes
────────────────────────────────────────────────────────
USER#123        PROFILE             name, email
USER#123        ORDER#1001          total, status        ← order của user 123
ORDER#1001      ITEM#sku-55         qty, priceSnapshot   ← item của order 1001
ORDER#1001      ITEM#sku-77         qty, priceSnapshot

→ "Lấy user + toàn bộ order" = 1 query theo PK=USER#123 (KHÔNG JOIN)
```

### Đánh đổi

| Được                                                   | Mất                                                            |
| ------------------------------------------------------ | -------------------------------------------------------------- |
| Đọc 1 lần ra cả "aggregate", latency phẳng ở mọi scale | Phải biết **trước** access pattern; thêm pattern mới → rất khó |
| Không JOIN, không N+1                                  | Mô hình khó đọc, khó ad-hoc query                              |
| Cost dự đoán được                                      | Denormalize cực mạnh → consistency tự quản lý ở app/stream     |

### 🎓 Bài học

Đây là đầu **cực đoan nhất** của trục denormalize: vứt bỏ cả khái niệm bảng-theo-entity. Chỉ hợp lý khi access pattern **cố định và đã biết rõ** (vd: cart, session, IoT). Với ecommerce có nhiều query linh hoạt như dự án này → **RDBMS chuẩn hóa vẫn đúng**, chỉ denormalize có chọn lọc (như `ProductSKUSnapshot`).

## Case Study 6: Bài Học Thất Bại — "Denormalized Order Object"

> Case **cảnh báo** từ Wesley Felipe (Medium) — denormalize sai chỗ.

### Diễn biến

- Team build một **"denormalized order object"**: một cấu trúc precomputed gộp mọi thứ app cần, để tránh runtime JOIN.
- _"On paper, it was the textbook move."_ — Trên giấy tờ trông rất chuẩn.

### Hậu quả

- Centralized denormalized state buộc phải có một **cơ chế recompute định kỳ** để sửa inconsistency do real-time flow tạo ra.
- Kết quả: **phức tạp hơn nhiều** so với dự kiến → đúng "Data Synchronization hell".

### 🎓 Bài học

Denormalize sai chỗ tạo ra đúng các **nhược điểm mà ZZ_22 liệt kê**: Update Complexity, Data Inconsistency Risk, Maintenance Cost. Luôn hỏi: _"Ai sẽ giữ dữ liệu này đồng bộ, và bằng cơ chế nào?"_ trước khi denormalize.

## 🧮 Decision Framework — "Có Nên Denormalize Không?"

Tổng hợp từ tất cả case study trên thành một **cây quyết định** dùng được ngay:

```text
                    ┌─────────────────────────────┐
                    │  Có bottleneck ĐO ĐƯỢC chưa? │
                    │  (EXPLAIN ANALYZE > ngưỡng)  │
                    └──────────────┬──────────────┘
                       NO          │          YES
                  ┌────────────────┘                └────────────────┐
                  ▼                                                   ▼
        ┌──────────────────┐                          ┌──────────────────────────┐
        │ GIỮ 3NF.          │                          │ Dữ liệu có IMMUTABLE       │
        │ "Premature        │                          │ tại 1 thời điểm không?     │
        │  denormalization  │                          │ (invoice, order price)     │
        │  is evil."        │                          └────────────┬───────────────┘
        └──────────────────┘                          YES           │          NO
                                                   ┌────────────────┘          └─────────┐
                                                   ▼                                      ▼
                                       ┌────────────────────┐         ┌──────────────────────────────┐
                                       │ SNAPSHOT pattern.   │         │ Read >> Write (ratio > ~10:1)? │
                                       │ (ProductSKUSnapshot)│         └───────────────┬────────────────┘
                                       └────────────────────┘         YES             │            NO
                                                                ┌─────────────────────┘            └──────────┐
                                                                ▼                                              ▼
                                              ┌──────────────────────────────┐              ┌────────────────────────┐
                                              │ Sync trong CÙNG database?      │              │ GIỮ 3NF + thêm INDEX.   │
                                              └───────────────┬────────────────┘              │ Tối ưu query trước khi  │
                                              YES             │            NO                 │ denormalize.            │
                                       ┌──────────────────────┘            └────────┐         └────────────────────────┘
                                       ▼                                            ▼
                          ┌──────────────────────────┐          ┌──────────────────────────────────┐
                          │ Trigger / Materialized    │          │ Sync RA NGOÀI DB (search/cache)?   │
                          │ View (DB tự maintain)      │          │ → Transactional Outbox + idempotent│
                          └──────────────────────────┘          └──────────────────────────────────┘
```

### Bảng quyết định nhanh theo loại dữ liệu

| Loại dữ liệu                 | Read/Write        | Consistency cần          | Kỹ thuật khuyến nghị                |
| ---------------------------- | ----------------- | ------------------------ | ----------------------------------- |
| Giá/tên tại thời điểm mua    | Write-once        | Strict (legal)           | **Snapshot** (`ProductSKUSnapshot`) |
| reviewCount, averageRating   | Read-heavy        | Eventual OK              | **DB Trigger** hoặc job định kỳ     |
| Listing/báo cáo sản phẩm     | Read-only         | Eventual OK              | **Materialized View**               |
| Sync sang search/email/cache | Mixed             | Eventual nhưng KHÔNG mất | **Transactional Outbox**            |
| Số dư ví / thanh toán        | Write-heavy       | Strict                   | **Giữ normalized + locking** (Uber) |
| Feed/timeline hot key        | Read-heavy + skew | Eventual OK              | **Hybrid fan-out** (Twitter)        |

## ✅ Checklist Trước Khi Denormalize

In ra và tick trước mỗi quyết định denormalize. Nếu còn ô chưa tick → **dừng lại, normalize tiếp**.

```text
[ ] 1. ĐO ĐẠC: Có số liệu EXPLAIN ANALYZE chứng minh JOIN là bottleneck thật?
[ ] 2. HOT PATH: Query này có nằm trên đường nóng (user-facing, high QPS)?
[ ] 3. AI MAINTAIN: Đã chỉ rõ CƠ CHẾ giữ đồng bộ (trigger/MV/CDC/outbox)?
       → KHÔNG được trả lời "application code sẽ tự nhớ update".
[ ] 4. CONSISTENCY: Domain này chấp nhận eventual consistency được không?
       → Nếu là tiền/đơn hàng/pháp lý → cân nhắc snapshot thay vì denormalize sống.
[ ] 5. RECONCILE: Có job định kỳ so stored vs actual để phát hiện drift chưa?
[ ] 6. IDEMPOTENT: Nếu sync qua event → handler có idempotent (dedup theo eventId)?
[ ] 7. ROLLBACK: Có kế hoạch revert nếu denormalization gây bug?
[ ] 8. DOCUMENT: Đã ghi lại lý do + trade-off (như chính file này)?
```

> 💡 Quy tắc 1 câu: **"Nếu không trả lời được 'AI sẽ giữ dữ liệu này đồng bộ, bằng cơ chế gì?' thì CHƯA được denormalize."**

## 🧠 Mental Model Tổng Hợp

```text
┌─────────────────────────────────────────────────────────┐
│  WRITE SIDE (normalized 3NF)   →  source of truth          │
│       │                                                    │
│       │   triggers / CDC / materialized view               │
│       ▼                                                    │
│  READ SIDE (denormalized)      →  query-optimized          │
└─────────────────────────────────────────────────────────┘

Domain quyết định mức consistency:
  • Chat / Feed / Analytics  → eventual OK   (Discord, Instagram)
  • Payment / Order / Invoice → strict       (Uber, ProductSKUSnapshot)

Quy tắc vàng:
  1. Normalize trước (3NF), denormalize sau khi ĐO được bottleneck
  2. Để DATABASE tự maintain dữ liệu denormalized (trigger / MV / CDC)
  3. KHÔNG phó mặc consistency cho application code
```

## 🛒 Áp Dụng Vào Dự Án NestJS Ecommerce

| Bài học enterprise                                    | Áp dụng trong dự án này                                                                                                 | Trạng thái                                                        |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Snapshot cho dữ liệu immutable (Uber/legal)           | `ProductSKUSnapshot` — `productName`, `skuPrice`, `skuValue`, `productTranslations` (Json) snapshot tại thời điểm order | ✅ Đã có trong schema                                             |
| Denormalize tránh JOIN nóng                           | `Brand.name` (tránh JOIN `BrandTranslation` cho default), `Product.name`, `Category.name`                               | ✅ Đã có trong schema                                             |
| Counter cache qua DB trigger (Discord-style maintain) | `Product.reviewCount`, `Product.averageRating`                                                                          | 💡 Đề xuất — **chưa có** trong schema, là ví dụ minh họa từ ZZ_22 |
| Read model tách biệt (CQRS / fan-out)                 | Materialized view `product_statistics` cho listing                                                                      | 💡 Đề xuất — chưa triển khai                                      |
| Soft delete giữ referential integrity                 | `deletedAt` + index `@@index([deletedAt])` trên hầu hết model                                                           | ✅ Đã có trong schema                                             |
| Transactional Outbox cho event sync                   | Thay thế `DomainEvent` fire-and-forget (`src/events/domain-event.base.ts`) khi cần đảm bảo không mất event              | 💡 Đề xuất — hiện đang fire-and-forget                            |
| Eventual consistency check                            | Job định kỳ so stored vs actual (mục "Data Consistency Checks" trong ZZ_22)                                             | 💡 Đề xuất khi thêm counter cache                                 |

> ⚠️ **Lưu ý độ chính xác:** Tại thời điểm viết, schema thật (`prisma/schema.prisma`) **chưa có** `Product.reviewCount` / `averageRating` và **chưa có** materialized view `product_statistics`. Chúng là **đề xuất minh họa** kế thừa từ ZZ_22, không phải code hiện hành. `ProductSKUSnapshot` và `Brand.name` là thật và đã denormalize đúng như mô tả.
>
> 📌 **Về events:** Dự án đã có kiến trúc event-driven (`src/events/`) với `DomainEvent` base + các handler (payment, price-alert, user-welcome). Chúng hiện là **fire-and-forget** — phù hợp cho side-effect không quan trọng (email chào mừng). Nhưng nếu dùng để **sync dữ liệu denormalized** (vd: cập nhật read-model khi giá đổi qua `ProductPriceChangedEvent`), nên nâng cấp lên **Transactional Outbox** để tránh mất event.
